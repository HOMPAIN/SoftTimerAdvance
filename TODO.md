# Известные проблемы библиотеки SoftTimerAdvance

Проблемы не исправлены. Обновлено 2026-09-30 после объединения 16- и 32-битных таймеров в один пул.

Пометка **[проверено]** значит, что проблема воспроизведена тестом на искусственном времени.

## Серьёзные

### 1. Библиотекой нельзя пользоваться из прерываний

**Где:** все методы интерфейсов (`STimer`, `SDelay`, `STimeout`) и `SoftTimerManager::AddManual`

- Поля `Config` — битовые, их изменение не атомарно. Если прерывание вызовет `Reset()`/`Stop()` в момент, когда основной цикл меняет `Config` того же таймера, одно из изменений потеряется.
- Счётчики 16/32 бита на 8-битном AVR пишутся по байтам. `Reset()` из прерывания во время `Tick` может дать испорченное значение счётчика.
- Защита `Lock` в `AddManual` не атомарна: проверка и установка `Lock`, `Count16++`/`Count32++` и расчёт свободного места не защищены. При добавлении таймера из прерывания во время добавления в основном цикле два таймера могут занять одну ячейку или пулы 16 и 32 бит могут наложиться друг на друга.

Сброс таймаута из прерывания (например, по приёму байта) — естественное применение, поэтому проблема важная.

**Как исправить:** критические секции (запрет прерываний) вокруг изменения таймера, либо явно запретить вызовы из прерываний в документации.

### 2. «Висячий» указатель на отложенный запуск

**Где:** `SoftTimerManager::Working`, удаление таймера без `DeleteProtection`

`AddDelayCall` освобождает ячейку после срабатывания, а указатель `SDelay*` у пользователя остаётся. После следующего `Add*` этот указатель управляет уже чужим таймером (`Reset`, `Delete`, `ForceCell` попадут в другой таймер).

Похожий случай: функция таймера удаляет свой таймер (`Delete`) и тут же добавляет новый. Новый таймер займёт ту же ячейку, и код после вызова функции (`timer_base->Func = 0` для таймеров без `DeleteProtection`) сразу его удалит.

Следствие: `SDelay::Reset()` из собственной функции не перезапускает отложенный запуск, если не включён `SetDeleteProtection(1)`.

**Как исправить:** например, номер поколения в ячейке и проверка его в интерфейсе, либо не возвращать указатель для разовых запусков без защиты от удаления.

### 3. TaskDelay под if/for/while без фигурных скобок работает неверно [проверено]

**Где:** макросы в `src/SoftTimerAdvanceTask.h`

Макрос состоит из нескольких операторов и начинается с `;` (точка с запятой стоит в имени макроса: `#define TaskDelay(X); ...`). Код

```cpp
if (условие)
    TaskDelay(5000);
```

выполняет задержку всегда, независимо от условия. Ошибок компиляции нет. То же с `for`/`while` без скобок.

**Как исправить:** убрать `;` из определений и обернуть тело в `do { ... } while (0)` (метка `case` внутри `do-while` внутри `switch` допустима).

## Средние

### 4. Повторный STTask::Start у работающей задачи теряет ячейку пула [проверено]

**Где:** `STTask::Start` (`src/SoftTimerAdvanceTask.cpp`), ветка `if(Line!=0)` пустая

Создаётся второй таймер, первый остаётся в пуле навсегда (он защищён от удаления, указатель на него потерян). Задача при этом начинается заново.

Кроме того, `Line == 0` всё время, пока выполняется тело задачи (между задержками), поэтому в это время `IsRunning()` возвращает 0, а `Abort()` ничего не делает.

### 5. Нет проверок на 0

`Add*` возвращает 0, когда пул заполнен.

- `STTask::Start` сразу вызывает `Timer->SetDeleteProtection(1)`.
- Примеры `examples/Timeout` и `examples/ESP32Sleep` не проверяют результат `Add*`; Timeout сразу вызывает `RxTimeout->Reset()`.
- Методы интерфейсов `STBase`/`STimer`/`SDelay`/`STimeout` не проверяют `this`.

### 6. Память удалённых таймеров возвращается в пул не сразу и не вся [проверено]

**Где:** `SoftTimerManager::Working` (уменьшение `Count16`/`Count32`), `AddManual`

`Count16`/`Count32` уменьшаются только когда перебор в `Working` доходит до последней ячейки своего разрешения и она свободна. Поэтому:

- сразу после удаления 16-битных таймеров 32-битный таймер может не добавиться, хотя память уже не используется (нужно несколько вызовов `Update`);
- если удалены все 16-битные таймеры, кроме последнего добавленного, их память недоступна для 32-битных, пока жив последний (и наоборот).

Удалённые ячейки повторно используются таймерами того же разрешения, а 16-битный таймер может занять свободную 32-битную ячейку. Обратное невозможно.

**Как исправить:** в `AddManual` перед отказом убирать свободные ячейки с конца обоих пулов.

### 7. Время отсчитывается от последнего Update, а не от момента добавления или сброса [проверено]

**Где:** `SoftTimerManager::Tick`

Если между `Update` и `Add*`/`Reset()` прошло время (долгая функция таймера, `delay()` в `loop`), следующий `Update` прибавит новому таймеру всё время с предыдущего `Update`.

Пример: с последнего `Update` прошло 400 мс, добавлен `AddDelayCall` на 1000 мс — он сработает через 600 мс. То же с `Reset()` таймаута.

При быстром `loop()` ошибка мала.

### 8. Таймеры в секундах срабатывают раньше на время до 1 с [проверено]

**Где:** `SoftTimerManager::DtDiv1000` / `Tick`

Секундные «тики» привязаны к часам менеджера, а не к моменту добавления таймера. `AddDelayCall` на 3 с, добавленный на 900-й мс, сработал через 2100 мс.

То же для миллисекундных таймеров при `Update(micros())` — ошибка до 1 мс.

Касается и 16-битных таймеров, переведённых в секунды (см. п. 9).

### 9. Ограничения 16-битных таймеров

- Счётчик останавливается на 65535. Если между вызовами `Update` проходит больше (65535 − период) единиц таймера, лишнее время теряется. Микросекундные таймеры по этой причине по умолчанию создаются 32-битными.
- `SetPeriod`/`SetTimeout`/`Reset` со значением больше 65535 переводят таймер в более крупные единицы с округлением (90500 мс → 91 с), точность падает (см. п. 8).
- Значение больше 65535 секунд молча обрезается до 65535 с.

**Как исправить:** возвращать признак ошибки или пересоздавать таймер как 32-битный.

### 10. Требования к источнику времени для Update

- Источник должен быть 32- или 64-битным счётчиком. Счётчик меньшей разрядности при переполнении даст ложный скачок времени.
- Между двумя вызовами `Update` не должно проходить больше 2^32 единиц источника (71,6 мин для микросекунд, 49,7 суток для миллисекунд).
- Если время пошло назад (даже на 11 мс), приращение получается около 2^32, счётчики всех таймеров упираются в максимум, и таймеры в строгом режиме срабатывают подряд тысячи раз. **[проверено]** С `millis()`/`micros()` такого не бывает, со своим источником возможно.

**Как исправить:** приращение больше 2^31 считать шагом назад и игнорировать.

## Недописанное

### 11. Телеметрия времени работы функций не работает

**Где:** `SoftTimerManager::Working`, `SoftTimerTelemetry_pp`

- `work_time = uSeconds - time_start` всегда 0: `uSeconds` не меняется, пока выполняется функция таймера. Нужен собственный источник времени (например, указатель на функцию `micros`).
- Вызов `Telemetry.Tick` закомментирован, поэтому `CPULoad` и `MaxWorkTime` не считаются.
- WatchDog по той же причине никогда не срабатывает.
- `Telemetry.MaxWorkTime` имеет тип `int16_t` и сравнивается с `uint32_t` (предупреждения `-Wsign-compare`), при значениях больше 32767 мкс станет отрицательным.

### 12. Режим StrictMode нельзя выбрать

Все `Add*` создают таймер в строгом режиме (0), метода для смены режима нет. Режимы 1 и 2 в `Working` недостижимы и не проверены.

В строгом режиме после долгой паузы таймер вызывается подряд столько раз, сколько периодов пропущено (таймер 1 мс после паузы 5 с — 5000 вызовов).

### 13. Задачи (STTask)

- Нет ожидания дочерней задачи: `StartChild` запускает её, но родитель не узнаёт о завершении. Поле `TaskParent` нигде не используется.
- Переменные задачи статические, поэтому одну функцию нельзя запустить в двух `STTask` одновременно.
- Два `TaskDelay` в одной строке исходника дают ошибку компиляции (одинаковые `case`), `TaskDelay` внутри собственного `switch` пользователя работать не будет.
- Запуск требует приведения `(PrmFuncST)TaskFunc`. Вызов функции через указатель другого типа формально является неопределённым поведением; на практике работает. Лучше добавить перегрузку `Start` для `void(*)(STTask*)`.

## Мелкие

### 14. Имена

- Опечатки в публичных именах: `ForceCell` (ForceCall), файлы `SoftTimerAdvanceManger.*` (Manager), `LastFanc` (LastFunc). Позже переименование сломает совместимость.
- Значения перечислений `Seconds`, `Milliseconds`, `Microseconds`, `Bits16`, `Bits32`, `BitsAuto` попадают в глобальную область имён и могут конфликтовать с другими библиотеками.

### 15. library.properties и README

- Версия 1.0.3 не поднята, хотя интерфейс изменился: `Init` без разрешения, поля `Count16`/`Count32` вместо `Count`, периоды `uint32_t`, удалены 64-битные таймеры, `Update` возвращает время до следующего таймера.
- README не описывает таймауты, выбор разрешения и ограничения 16-битных таймеров.

### 16. Тестовый проект Windows и предупреждения

- `examples/WindowsTestProj` использует набор инструментов v145, в Visual Studio 2022 (v143) без правки не собирается.
- Предупреждение C4099: `STTask` объявлен как `class`, а в полях указан как `struct`.

### 17. Устаревшие комментарии

- `examples/Task/Task.ino`, строка 2: описание скопировано из примера DelayCall.
- `SoftTimerAdvanceStructures.h`, поле `Delay`: «если 0 то таймер вызывается 1 раз и удалёется» — сейчас это не так, тип таймера задаёт `Config.Type`.
